# Handoff 2026-09-23 — STC-413, the library as a view over a folder

STC-413 shipped (PR #198, merged 2026-09-23). This records what moved, what was
got wrong, and what is still open — in the shape `HANDOFF-2026-09-04-STC-309.md`
set.

---

## What it does

The library stopped being a store the app owns. It is a **view over a
user-chosen folder**:

```
<saveFolder>/
├── login-bug.mp4                  finished recording — the filename IS the label
├── error-state.png                finished still
├── holiday.mp4                    foreign file — listed, reduced metadata, no Edit
└── raw/
    └── 2026-09-22_14-30-01/       the bundle behind login-bug.mp4
        ├── anchors.json  capture.json  events.json  project.json
        └── display.mp4            raw, cursorless — source, never the deliverable
```

Three rules carry it: **top level means finished**, **the filename is the
name**, **`raw/` holds source material**. Every library signal falls out of one
of them — duration and dimensions from the container header, kind from the
extension, edited-status from location.

A finished file carries an opaque id **in its own bytes** (`cap_` + 26 Crockford
chars): a trailing ISO-BMFF `uuid` box in MP4, an XMP `iTXt` chunk in PNG. That
is the whole mechanism by which a rename or move in Finder cannot break the link
back to a bundle.

## Two deviations from the ticket, taken deliberately

**Metadata is EMBEDDED, not a sidecar.** STC-413's 2026-09-21 scope decision
specified a sidecar. Reversed during design because the ticket's own reasoning
argued against it: Obsidian — the model it cites — does not use sidecars. Its
metadata is frontmatter *inside* the file, which is exactly why it survives a
move. A sidecar is a second object and only survives if the user moves both
halves.

**`take.json` is retired for finished captures.** The filename is the label.

Both are recorded as a comment on the Linear ticket, which was left OPEN — the
code shipped but the runbook has not been run.

## What was got wrong, and is worth not repeating

**A clean merge is not a correct merge.** PR #199 (STC-407) landed on master
while STC-413 was in flight, cleaning up Still→Shot rename residue. STC-413's
branch was cut before it, and its new `looseFileItem` code path reintroduced
`badge: "Still"`. The two merged **without a textual conflict** because they
changed different lines — the collision was semantic. Nothing caught it: not
CI, not review, not the merge. It was found only by diffing the merged branch
against master afterwards, which costs one command. Fixed in PR #200.

**Two Criticals survived every per-task review and were caught only by running
the code**, in a whole-branch review at the end:

- *No still was ever linked to its bundle.* ImageIO routes
  `kCGImagePropertyPNGDescription` into XMP inside an `iTXt` chunk, NOT a
  `tEXt` chunk keyed `Description`. The reader walked `tEXt` only. The Swift
  test asserted the properties dictionary contains the key — true, and blind to
  where it lands. **A round-trip test against the real encoder is the only
  thing that could have caught it**, and `helper/test/still-encode.test.ts` now
  has one.
- *Any export over ~80 s lost its id and its facts.* `locateMoovBytes` re-capped
  its follow-up read at the same 64 KB. `moov` grows 11-14 bytes per sample, so
  it passes 64 KB at ~4,600-5,800 samples — 80-95 s at 60 fps. It also turned
  the export guard against the user: re-exporting a long take refused with
  *"it belongs to a different capture"*, a confident lie about their own file.

**The recurring failure mode of this whole ticket was a test that could not
fail**, not a test that failed:

- Task 3's MP4 truncation passed a test asserting "the original bytes survive
  as a prefix" — because a *truncated* prefix is still a prefix. It reduced an
  83,894-byte fixture to 82 bytes.
- The library's sort test was vacuous twice over. First the fixture contradicted
  its own comment; then, corrected, it still could not discriminate, because a
  matched item's `id` IS its bundle's stamp and its `createdAt` is `stampToMs`
  of that same stamp — so id-ordering and time-ordering are mathematically
  identical for matched items. Only an *unmatched* item can tell them apart.
  Then it had a timezone bug. Three passes over one test.
- Task 13's rename worked perfectly on disk and changed nothing on screen,
  because `label` was cleared on a match and `id` is deliberately immune to
  renames. Every test passed.

**A `moov` larger than the read window is not what a test named
"larger-than-the-window capture" covers.** That test used a fixture whose FILE
is 83 KB and whose `moov` is 1,275 bytes. It proves the multi-hop walk and is
one word away from the case that was broken. It has been renamed.

## Known limitations, stated rather than discovered later

- **A JPEG still carries no readable id** and is never matched to its bundle —
  it lists as a loose file while its bundle lists separately. **HEIC
  unexpectedly DOES carry one**; only JPEG is broken. The standing alternative
  is making stills PNG-only, which also deletes STC-293's flatten-conflict fork.
  Undecided.
- **The orphan sweep will rarely fire.** It removes a bundle only when
  orphanhood is *provable* — every top-level file yielded a readable id and none
  matched — so one untagged PNG (a ⇧⌘4 screenshot, a downloaded image) blocks a
  whole pass. That is the safe direction for something that deletes data, but
  the feature ships close to inert. **Decided 2026-09-23: replace it with a
  user-initiated "Reclaim space" that shows what it would remove.** Not yet
  filed.
- **A corrupt `capture.json`** on an already-exported capture leaves two tiles
  until one is deleted. Warns on stderr — which nobody sees in a packaged app;
  `showMessageToast` exists. Refusing to export instead would cost a take over a
  bookkeeping file. Salvaging the id from the corrupt bytes would close it, and
  belongs in `ensureCaptureId` (the writer), NOT in `readBundleId` — a reader
  that repairs reintroduces the multiple-owners defect.
- **The 4000 ms scan backstop is calibrated on one Mac**, measured INSIDE the
  full suite (227-748 ms; it reads ~40 ms in isolation, which is what made the
  first number wrong). CI has never run it. It catches a severe quadratic
  regression and deliberately not a 2x slowdown.

## Not verified — `docs/STC-413-RUNBOOK.md`

Nothing here has opened a tagged export in QuickTime, renamed a still in Finder
on real hardware, or run any browser gate. The 500-file scan test pins per-file
**overhead**, not IO throughput — 500 real 4K exports add ~32 MB of scattered
reads it never touches.
