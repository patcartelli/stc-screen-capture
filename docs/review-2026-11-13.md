## 1. Where it stands

The centre still holds. `render(project, session, t)` is still the only transform, both sinks
call it, and every gate passed here on real Chrome. Nine of the eleven proposals from the
September review are done (section 7). The defects found this time are, again, at seams: the
edges of the zoom geometry, the supervisor's state after a helper death, test fixtures that
reach the real machine, and documents that describe an app that no longer exists.

Three things matter before the beta (STC-647):

1. **A manual zoom region has no minimum size.** A drag that starts at the edge of the frame
   saves a zero-size crop. The picture becomes one flat colour for the length of the zoom. (Finding 1.)
2. **A click outside what was recorded still opens an auto-zoom**, and the picture zooms into
   the nearest corner. This is on by default for every area and window take, and for any take
   on a Mac with a second display. (Finding 2.)
3. **The README's Quick Start describes a main-window Record button, a Scope picker and
   `~/Desktop/stc/`, none of which exist.** The repo is public. (Finding 9.)

The app was walked by hand after the first version of this report (section 11). The walk
covered the Record flow from the menu bar and the hotkey, the recording panel, the Library's
empty state and Settings. It did not cover a Shot or either editor.

## 3. Findings

Each has a lens tag: **[C]** correctness, **[T]** test trust, **[A]** architecture,
**[Y]** a11y and states, **[U]** UX and copy. None of these has a Linear ticket (the open
Capture backlog on 2026-11-13 is STC-646, 647, 650, 651, 652 and the CleanShot set).

### Tier 1 — fix before the beta

**1. [C] A manual zoom region can be saved at zero size, or far smaller than any zoom the
editor's own Amount control allows.**
`rectFromGesture` (`transform/src/zoom-override.ts:360-380`) sizes a dragged box by
`min(drag, room to the edge)`. A drag that starts on the frame's edge and heads outward has no
room, so the box is 0 × 0. A drag that starts 0.5% from the edge gives a 0.005 box, a 200×
zoom. Nothing downstream refuses it: `cleanOverrideRect` (`transform/src/trim.ts:344-349`)
accepts any four finite numbers, and `frameShaped` (`zoom-override.ts:334-340`) returns a
square unchanged. The Amount slider is clamped to 1.1×–4× (`app/src/override-edit.ts:56-57`),
so the drag reaches sizes the slider forbids. At full zoom the crop is a point: the export
shows one flat colour where the picture was, with no pointer (seen in a real export, section
12), and at an amount of exactly 1 the cursor scale is `1 / 0`.

```
A drag from near right edge outward: { x: 0.995, y: 0.5, width: 0.005, height: 0.005 }
A drag from the edge itself:         { x: 1, y: 0.5, width: 0, height: 0 }
  magnification at amount 1:         { x: Infinity, y: Infinity }
A 2.5% drag:                         { x: 0.5, y: 0.5, width: 0.025, height: 0.025 }
```

(Output of a throwaway script calling the real functions; not committed.) Same class as
STC-385: a crop that renders black with no error. The editor path is `editor.ts:1805-1829`
(`stageUv` clamps the pointer to 0..1, so the edge is reachable). A hand-edited
`project.json` with a negative or oversized rect goes through the same hole.

**2. [C] A click outside the recorded area opens an auto-zoom into the nearest corner.**
`zoomWindows` (`transform/src/zoom.ts:124-155`) builds windows from every down/up event and
never asks where the click landed. For a window with no change track, `deriveFromCursor`
(`transform/src/zoom-change.ts:289-302`) maps the click to capture UV, which is outside 0..1,
and `finishCrop` → `clampRectToFrame` slides a 0.5 square to the closest corner. Nothing
filters events to the capture: `session.ts` and the helper keep every global event.

```
B  region take, click outside the region:  window [700 ms, 3580 ms]
                                            crop { x: 0.5, y: 0.5, width: 0.5, height: 0.5 }
B2 whole-display take, click on a second display to the right:
                                            crop { x: 0.5, y: 0.083, width: 0.5, height: 0.5 }
```

Zoom is on by default (`trim.ts:298`) and `take-project.ts` seeds no exception for area or
window takes. So an area recording of a dropdown, with one click in another app during the
take, zooms 2× into a corner of the dropdown for about 2.9 seconds. The workflow study
(`docs/STC-382-WORKFLOW-STUDY.md`) records the decision that area scope and auto-zoom are two
regimes because "you wouldn't zoom a crop". The code does not carry that decision.
Not verified on a real two-display take: one display here.

### Tier 2 — fix soon

**3. [C] Stage 2's change classifier has no magnitude floor, so one stray cell moves the
crop.** This is the answer to "what filters caret blink, spinners, hover trails and toasts".
`classifyCells` (`zoom-change.ts:169-206`) has three tests: active in ≥ 80% of frames is
ambient (a spinner, a video); a cell's share of change inside a burst window must be ≥ 0.5;
and it must beat the burst's share of frames by 0.25. All three are ratios of a cell against
itself. `CELL_ACTIVE_FRACTION` (0.05) is used only by the ambient test. So a cell with one
0.05%-of-a-cell change that happens to fall within 600 ms of the click scores a share of 1.0
and survives, and the crop is the bounding box of every survivor:

```
C  clean reaction near the click:               crop { x: 0, y: 0.056, width: 0.5, height: 0.5 }
C  same, plus one 0.0005 blip in the far corner: crop { x: 0.228, y: 0.289, width: 0.7, height: 0.7 }
     far cell class: survivor
```

A clock tick, a notification badge, a hover highlight under the pointer on its way to the
click, or a toast that appears with the click all have this shape. A blinking caret mostly
fails the 0.5 share (its changes are spread evenly), and a spinner fails the ambient test.

**The temporal-filter rules do not exist anywhere.** STC-319 is marked Done, its deliverable
was "the rules, as a list", and `zoom-change.ts:18-30` says in its own header that the list
was never written and the thresholds are reasoned, not measured. STC-486 added `BURST_MARGIN`
from one Meet take. This is still open, just not ticketed.

It is latent today: nothing in the app writes `changes.json`. `computeChangesForVideo`
(`transform/src/change-track.ts`) is reached only by `harness/` and
`scripts/change-track-one.mjs`, so every take in the shipped app uses the cursor fallback
(finding 2's path). It goes live the day the change pass is wired in.

**4. [C] The pill and the menu bar's "Stop Recording" can outlive a take whose helper died.**
The supervisor emits `recording-lost` while `state` still reads `"recording"`, and sets
`"starting"` or `"failed"` only after the emit returns (`app/src/supervisor.ts:359-387`).
The pill's handler for that event is `reconcile()`, which reads `sup.state`
(`app/src/pill-window.ts:383`, `356-366`), so it does nothing. `main.ts:1086-1088` already
documents this ordering, for a different consumer. After one crash the next heartbeat from
the respawned helper heals it. After the fourth crash in ten seconds the supervisor gives up
(`supervisor.ts:374-382`): no helper, no heartbeat, and nothing listens for `gave-up` on the
pill's behalf. The pill stays on screen with a frozen timer, its Stop does nothing
(`pill-window.ts:265` refuses when state is not `recording`), and the tray's reconcile has the
same gap (`main.ts:920`). No test covers it: nothing in `app/test/pill*.ts` kills the helper.

**5. [C] The supervisor heals one direction only (September's P6, still open).**
`startRecording` sets `recording` only when `start` is answered (`supervisor.ts:62-68`). If
the request times out client-side and the helper then succeeds, the helper is recording and
the app says idle. The heartbeat check only covers `recording → idle`
(`supervisor.ts:341`). The pill for that take was already discarded (`main.ts:2220`), so a
take is recording with no pill and a menu that says Record. macOS's own indicator is the only
sign. Not reproduced; reasoned from the code as in September.

**6. [A] Test seams are live in the packaged app, and one of them swaps the helper binary.**
`resolveHelperPath` returns `STC_HELPER_BIN` before it looks at `isPackaged`
(`app/src/helper-path.ts:20-23`, wired at `main.ts:140-145`). The helper is a child of
Capture, which is the arrangement that gives it Capture's Screen Recording, Input Monitoring,
Camera and Microphone grants. So any process that can launch Capture with one environment
variable set runs its own binary under those grants. `STC_ASSUME_PERMISSIONS=granted`
(`main.ts:715`, `747`) skips the permission gate the same way, and
`STC_CAPTURE_FAULT` reaches the shipped helper (78 references in `helper/src`), along with
`STC_KEY_INJECT`, which feeds synthetic keystrokes into a take (`Capture.swift:2563-2579`).
None is gated on `app.isPackaged`. Related and **not verified on a built app**:
`electron-builder.yml` sets no Electron fuses, so `ELECTRON_RUN_AS_NODE` is presumably still
on in the signed build, which is the better-known route to the same result.

### Tier 3 — smaller, or drift worth recording

**14. [C] `parseProject` takes any integer as the output size.** `trim.ts:173-174` accepts
`output.width`/`height` if `Number.isInteger`, so 0, negative, odd, or an aspect that is not
the capture's all load. `output-size.ts` is described as the one place the even and aspect
rules are enforced, and the parser does not go through it. An odd size fails H.264 at export;
a wrong aspect stretches an unframed take. Reachable by hand edit only, which
`docs/STC-313-RUNBOOK.md` tells the reader to do.

**15. [C] Two IPC handlers trust the renderer more than the rest do.**
`still:startDrag` (`main.ts:3898-3905`) checks only `existsSync(file)` before reading the
path as an image and starting a drag of it; every sibling handler checks `insideCaptureRoot`.
`preview:chunk` (`main.ts:4604-4613`) validates `length > 0` with no ceiling before
`Buffer.allocUnsafe(length)`. Neither is reachable without a compromised renderer.

says so (`zoom-override.ts:199-206`, `256-261`: "getting overlap right is explicitly not this
phase's job") and a retime (STC-329) removes the merge-gap guarantee for derived windows too.
Acknowledged in code, not ticketed, not seen on screen.

## 4. The seven areas, answered

1. **Crop, zoom, compositing.** Two new defects of the STC-385/387 class (findings 1, 2) and
   one validation hole (14). What holds: every tuned crop goes through `frameShaped`, stage 2
   uses one shared size, the cursor takes the same crop step as the picture
   (`render.ts:447-449`), `frameSize` reads `displayWidth` for a `VideoFrame`
   (`compositor.ts:43-47`), and a refit maps through `contentRect`. Retina: the map is
   output over points, so backing scale cancels. Not checked on hardware: two displays, a
   real refit, a moved window (`scope.window.track`).
2. **Change-track noise.** Finding 3. The rules list does not exist. The filter that exists
   handles continuous change and evenly spread change, and does not handle a small one-off
   change that coincides with the click.
3. **Capture lifecycle.** The purge is sound: it runs from the first recovery offer, never
   from the take's age (`temp-takes.ts:233-252`), and an unoffered take is never deleted.
   The helper's shutdown now waits for its stop (`main.swift:765-795`) and a start that
   finishes after a stop is answered and torn down (`main.swift:416-427`). Of the four
   failure states, each has a stop reason or warning, a line in `stop-copy.ts`, a fault
   injector and a grant test. I read the paths and ran none of them: they need grants.
   Pause exists only in the helper (finding 22).
4. **Window model.** Finding 4 is the one way the pill outlives a take. Otherwise it is made
   before `start`, shown only off confirmed state, and ended on every stop path
   (`pill-window.ts:168-182`, `278-292`). Position resets per take by construction (a new
   window each time). Space-switch survival and the library hide/return are set up in code
   (`pill-window.ts:148`) and were not watched.
5. **IPC and settings.** 79 registrations, every one exposed and handled, no orphan
   channels. Path arguments are checked against the takes, temp or capture root, with a
   separator-aware test (`takes.ts:26`, `temp-takes.ts:99`). The two exceptions are finding
   15. `recorder:setSettings` strips the main-only keys. No handler checks the sender's
   frame; scoping is by which preload a window loaded.
6. **Editor and renderer.** STC-596–607 have landed. Finding 12 (size), 17 and 18 (a11y),
   21 (type). The header, tabs, ruler, trim handles and look grid have keyboard paths and a
   focus ring; `editor-a11y.e2e.test.ts` pins some of it.
7. **Packaging and identity.** True today: `appId com.studiocartelli.capture`, product name
   Capture, package name still `stc-screen-recorder` (`package.json:2`), signed with the
   self-signed "STC Dev Signing" identity, hardened runtime on, no fuses configured, helper
   shipped as `Contents/Resources/stc-helper`. Not notarized; STC-647 and STC-651 own that.
   Finding 6 is the packaging-relevant risk. No packaged build was made or inspected here.
